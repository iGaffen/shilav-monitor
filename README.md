# shilav-monitor

בודק כל 10 דקות, בין השעות 07:00-23:00 בישראל, את העמוד
[lp.vp4.me/jzze](https://lp.vp4.me/jzze), ושולח התראת טלגרם בשני מקרים:

1. **מעבר סגור → פתוח**: אם העמוד עבר ממצב "סגור" (המחרוזת "המלאי אזל" קיימת בעמוד) למצב "פתוח"
   (המחרוזת לא נמצאת) — זו ההתראה העיקרית, וההודעה שלה מציינת שהעמוד נפתח להזמנה.
2. **כל שינוי אחר בעמוד**: כל הרצה בונה "תמונת מצב" מנורמלת של התוכן הנראה בעמוד — כל שורות
   הטקסט, כל כתובות הקישורים (`href`), וכל מקורות התמונות (`src`) — ומשווה אותה לתמונת המצב
   מההרצה הקודמת. כל שינוי — כפתור או קישור חדש שמופיע, טקסט שנערך, תמונה שהוחלפה או נוספה —
   שולח התראה נפרדת עם קטע diff שמראה בדיוק מה השתנה, כדי שתוכלו לבדוק ידנית. תגיות `<script>`,
   `<style>` והערות HTML מוסרות לפני ההשוואה, כדי שרעש טכני (כמו timestamp בתוך קוד מעקב) לא
   ייצור התראות שווא — אבל אם באתר יש אלמנט דינמי גלוי שמשתנה בכל טעינה (למשל מונה "X צופים
   כרגע"), הוא כן ייצור התראה בכל הרצה, ואז יהיה צריך לצמצם את מה שנבדק.

**חשוב:** ה-10 דקות בפועל מגיעות משירות חיצוני (cron-job.org) שקורא ל-GitHub API כל 10 דקות
ומפעיל את ה-workflow. הסיבה: ה-`schedule` המובנה של GitHub Actions הוא best-effort ומתעכב
משמעותית בתדירויות גבוהות (ראו סעיף "איך לוודא" למטה). ל-GitHub Actions עדיין יש `schedule`
משלו, אבל הוא רץ רק פעם בשעה כרשת ביטחון — למקרה שהשירות החיצוני נופל — ולא כמנגנון הבדיקה
העיקרי.

כל בדיקה נשלחת עם headers של `Cache-Control: no-cache` / `Pragma: no-cache` ועם פרמטר
cache-busting ייחודי בכתובת (timestamp), כדי לוודא שאף CDN או proxy שיושב מול העמוד לא יחזיר
עותק ישן שנשמר בזיכרון מטמון — כל בדיקה מביאה את התוכן העדכני ביותר בפועל. כל הרצה רצה בתהליך
נקי ללא cookies או מטמון שמור מהרצה קודמת (בדומה לגלישה ב-incognito), כך שאין מצב session ישן
שמשפיע על התוצאה.

בנוסף, פעם ביום (בהרצה הראשונה אחרי חצות UTC) נשלחת הודעת "heartbeat" קצרה שמאשרת שהבדיקה
עדיין רצה כרגיל — כדי לדעת שהתהליך לא קרס בשקט.

יש ארבע רשתות ביטחון נוספות:

- **הפניה (redirect)**: אם ה-URL הסופי אחרי הבקשה שונה מהכתובת המקורית — נשלחת התראה נפרדת
  ומיידית, כי זה סימן חזק שהעמוד השתנה או שמפעילים תהליך רכישה בכתובת אחרת.
- **כשלים ברצף**: אם הבדיקה עצמה נכשלת (שגיאת רשת, timeout וכו') 3 פעמים ברצף — נשלחת התראה
  שהמערכת לא מצליחה לבדוק את העמוד, כדי שתדע שיש בעיה גם אם היא לא קשורה למצב המלאי.
- **קצב בדיקות שירד**: כל הרצה בודקת כמה זמן עבר מאז ההרצה הקודמת. אם עברו 40-300 דקות (יותר
  מהקצב הרגיל של 10-15 דק', אבל פחות מהפער הלילי הצפוי) — נשלחת התראה שה-trigger החיצוני
  (cron-job.org) כנראה הפסיק לעבוד, וכרגע רק רשת הביטחון השעתית של GitHub עדיין רצה. זה בדיוק
  התרחיש שבו הבדיקות "מצליחות" בלי שגיאה אבל בקצב איטי בהרבה — בלי הרשת הזו לא היה שום דבר
  שמתריע על כך.
- **כשל ברמת ה-workflow**: שלוש הרשתות למעלה מכוסות בתוך `monitor.py` עצמו — אבל אם שלב אחר
  ב-workflow נכשל (למשל push של `state.json` שנדחה כי הרצה מקבילה כבר דחפה קודם), הבדיקה
  בתוך `monitor.py` כבר הצליחה ולא הייתה יודעת להתריע. שני חלקים סוגרים את הפער הזה:
  - שלב ה-commit/push מנסה מחדש עד 5 פעמים (עם `git pull --rebase` בין ניסיון לניסיון) לפני
    שהוא נכשל בפועל, כדי שריצות מקבילות (הטריגר החיצוני מול רשת הביטחון השעתית) לא ידרסו
    אחת את השנייה.
  - שלב נוסף עם `if: failure()` רץ בסוף ה-job רק אם שלב קודם נכשל, ושולח התראת טלגרם עם
    קישור ישיר ללוג של אותה הרצה ב-Actions — כך שכל כשל ברמת ה-workflow (ולא רק כשל בבדיקת
    העמוד עצמה) מגיע להתראה.

זהו כלי ניטור פסיבי בלבד: GET רגיל עם headers סטנדרטיים, בלי scraping אגרסיבי ובלי כל ניסיון
לעקוף חסימות.

## איך זה עובד

- `monitor.py` — מבצע GET לעמוד, בודק את קיום המחרוזת (closed/open), ובנוסף בונה תמונת מצב
  מנורמלת של הטקסט/קישורים/תמונות ומשווה אותה לתמונת המצב הקודמת ב-`state.json`. שולח הודעת
  טלגרם הן על מעבר closed → open והן על כל שינוי אחר בתמונת המצב.
- `state.json` — מצב אחרון (`open`/`closed`) ותמונת המצב האחרונה של תוכן העמוד
  (`content_snapshot`), מתעדכנים אוטומטית ע"י ה-workflow.
- `.github/workflows/monitor.yml` — מגדיר את ה-workflow. הטריגר העיקרי הוא `workflow_dispatch`
  (מופעל חיצונית ע"י cron-job.org כל 10 דקות), ובנוסף `schedule` פנימי של GitHub שרץ פעם בשעה
  כרשת ביטחון בלבד. מבצע commit ל-`state.json` אם הוא השתנה.

### הגדרת הטריגר החיצוני ב-cron-job.org

1. הרשמה חינמית ב-[cron-job.org](https://cron-job.org).
2. יצירת GitHub personal access token (fine-grained), עם הרשאת `Actions: Read and write`
   על ה-repo הזה בלבד.
3. יצירת cron job חדש ב-cron-job.org עם ההגדרות הבאות:
   - **URL**: `https://api.github.com/repos/iGaffen/shilav-monitor/actions/workflows/monitor.yml/dispatches`
   - **Method**: `POST`
   - **Headers**:
     - `Authorization: Bearer <הטוקן שיצרתם>`
     - `Accept: application/vnd.github+json`
     - `Content-Type: application/json`
   - **Body**: `{"ref":"main"}`
   - **תדירות**: כל 10 דקות, בין 07:00-23:00 בישראל (ניתן להגדיר את טווח השעות ישירות לפי
     אזור הזמן שלכם בממשק של cron-job.org — לא צריך להתחשב ב-UTC או בשעון קיץ/חורף שם).

הטוקן נשמר רק בצד cron-job.org (בהגדרות ה-job) ואינו נכתב בקוד או נשמר ב-repo.

### לגבי טווח השעות של ה-schedule הפנימי (רשת הביטחון) ושעון קיץ/חורף

ה-`schedule` הפנימי (רשת הביטחון פעם בשעה) רץ תמיד לפי UTC ולא מודע לשעון קיץ/חורף. הערך
הנוכחי (`4-19`) מניח שעון קיץ בישראל (IDT, UTC+3). כשישראל עוברת לשעון חורף (IST, UTC+2) —
בסביבות סוף אוקטובר — וחוזרת לשעון קיץ בסביבות סוף מרץ, צריך לעדכן ידנית את שני הגבולות של
טווח השעות ב-cron (ב-1 שעה בכל כיוון) כדי שטווח 07:00-23:00 הישראלי יישאר מדויק. (טווח השעות
שמוגדר ב-cron-job.org עצמו לא מושפע מזה, כי הוא מוגדר שם לפי אזור הזמן המקומי ישירות.)

## איך לוודא שהבדיקה באמת רצה כמתוכנן

ה-heartbeat היומי בטלגרם מאשר רק שהתהליך לא קרס — הוא לא מראה את כל ההרצות. כדי לראות בפועל
שכל הרצה קורית בזמן ובודקת את העמוד:

1. עברו ל-לשונית **Actions** ב-repo → **Monitor Shilav page**.
2. שם מופיעה רשימה של כל ההרצות, עם חותמת זמן מדויקת לכל אחת. עמודת ה-event מבדילה בין
   `workflow_dispatch` (הרצה שהופעלה חיצונית ע"י cron-job.org — אמורה להיות רוב ההרצות, כל
   10 דקות) לבין `schedule` (רשת הביטחון הפנימית של GitHub — פעם בשעה בלבד).
3. לחיצה על הרצה בודדת ופתיחת הלוג של השלב **Run monitor** מציגה שורה כמו:
   `previous=closed current=open redirected=False` — כלומר מה הסקריפט מצא בפועל באותה הרצה.
4. אפשר גם לבדוק בממשק של cron-job.org את היסטוריית ההרצות של ה-job עצמו — שם רואים אם
   הקריאות ל-GitHub API יצאו בזמן ובאיזה סטטוס הן חזרו.

שימו לב: הרצות מסוג `schedule` (רשת הביטחון הפנימית) רצות על בסיס best-effort של GitHub
ולא מבטיחות דיוק של דקה-דקה — בעומס גבוה ייתכן איחור. הרצות מסוג `workflow_dispatch`
(שמופעלות ע"י cron-job.org) אמורות להיות מדויקות משמעותית יותר, כי הן לא תלויות בתור
ה-schedule הפנימי הצפוף של GitHub.

## הגדרת Secrets (חובה לפני ההרצה הראשונה)

ב-GitHub, בתוך ה-repo:

1. עברו ל-**Settings** → **Secrets and variables** → **Actions**.
2. לחצו **New repository secret**.
3. הוסיפו secret בשם `TELEGRAM_BOT_TOKEN` עם ערך הטוקן של הבוט.
4. לחצו שוב **New repository secret**.
5. הוסיפו secret בשם `TELEGRAM_CHAT_ID` עם ה-chat id שלכם.

הסקריפט קורא אותם אך ורק דרך משתני סביבה (`os.environ["TELEGRAM_BOT_TOKEN"]` /
`os.environ["TELEGRAM_CHAT_ID"]`) שמוזרקים ע"י ה-workflow מתוך ה-Secrets — הם לא כתובים בקוד
ולא נשמרים בשום קובץ ב-repo.
